# PC アプリがファームウェアに求めること

ESP32（XIAO ESP32S3）に書き込むファームウェアは、別の担当のコードに決まる予定。リポジトリの `firmware/` は参考実装で、本番では書き込まない。この文書は、**PC アプリ（`app/`）がファームに何を求めるか**をまとめたもの。書き込み担当に渡し、ファームが確定したら PM がアプリ側をそれに合わせる。

機能は変えない（4 領域 × 回数 1 / 2 × 強弱 = 16 キー、キャリブレーション、飽和の棄却）。

## 必須（これがないとアプリが動かない）

| 項目 | アプリが知りたいこと |
|---|---|
| 接続 | USB シリアル（COM ポート）で PC とつながる。通信速度（例 115200 bps）が分かること |
| 見つける | アプリが「このポートが DeskAPI のボードだ」と分かる方法。例: アプリが何か送ると決まった返事が来る、または起動時・定期的に決まった行が出る |
| タップ | 叩くたびに 1 行: **どの領域か**（左上 / 右上 / 左下 / 右下）、**何回か**（1 回 / 2 回）、**強さ**（弱 / 強） |

- 1 回か 2 回かの判定（2 回目を待つ時間）はファーム側で行い、確定してから送ってほしい。アプリは届いたタップをそのまま 16 キーのどれかに当てる
- 行の形式（JSON・CSV・独自の文字列）は問わない。1 行 1 メッセージで、改行で区切られていれば、アプリ側で合わせる
- 起動ログなど関係ない行が混ざってもよい（アプリは読めない行を捨てる）

## あれば使う（なければその機能をアプリで止める）

| 項目 | 使いみち | ないとき |
|---|---|---|
| キャリブレーション | テーブルごとに閾値・強弱の境目・領域の判定を合わせる（任意のテーブルで成り立たせるため）。アプリから「校正モード」「ノイズ測定」「値の保存」を指示し、校正中は 1 打ごとに 4 ch のピークが届く | キャリブレーションボタンを押せなくする。判定はファームの既定値のまま |
| 校正済みかどうか | 未校正ならボタンに赤い点を付けて促す | 点を出さない |
| 飽和の印（FW-007） | ±1.4 V を超えた打を棄却する | 棄却しない |
| 生波形 | 回路の受入試験 T-01（1.65 V を中心に振れるか）を見る | 受入試験はテスターと書き込み担当の方法で行う |
| ファームの版 | 不具合の切り分け | 表示しない |

## おすすめ

形式を新しく決めるなら、`docs/protocol.md`（v1.1）にそのまま合わせてもらうのが一番早い。アプリはすでにこの形式で動いていて、テストもある。参考実装 `firmware/` の `lib/DeskApiCore/src/Protocol.*` に送受信のコードがある。

合わせない場合も、上の「必須」が分かれば、アプリ側に変換（アダプタ）を 1 つ足すだけで対応する。

## ファームが確定したら（PM の作業）

1. 書き込み担当から、通信速度・見つけ方・タップの行の形式・あれば校正の指示と返事を聞く（またはソースを受け取る）
2. ユーザーに Windows で実際の出力を記録してもらう: `app/` で `npm run serial-log -- COM5`（COM 番号は実際のもの）を実行し、各領域を 1 回・2 回、弱・強で叩く。保存されたログファイルを PM に渡す
3. そのログをもとに、`app/src/main/protocols/` にアダプタを足し、ログを流し込むテストを書く（Codex のタスクにする）
4. 歯車パネルやキャリブレーションなど、ファームが対応しない機能はアダプタの「できること」で止める
5. `docs/hardware-test.md` の 3 章（書き込みと受入試験）を、書き込み担当の手順に差し替える

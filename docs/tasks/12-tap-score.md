# 12 集めたログで検出器を採点する（tap-score）

`tools/tap-collect/` に足す。`app/` と `firmware/` には触らない（`app/` のコードは読み込んで使うだけ）。

## 背景

11 の tap-collect で、叩き方ごとのラベルが付いた生値が集まる。次に要るのは、**検出器にそのログを流し、どれだけ正しく当てたかを数字で出す**道具。

- 閾値や前処理を変えたとき（人でも AI でも）、良くなったかどうかをこの点数で決める
- **ハードコーディング（特定の机・特定のログへの合わせ込み）を防ぐ**。キャリブレーションに使ったログと、採点に使うログを必ず分ける。別の机・別の日のログで採点できるようにする
- 検出器は 2 つある。どちらをデモで使うか決まっていないので、両方を同じ物差しで採点できるようにする
  - `app`: このブランチの `app/src/main/protocols/detector.ts`（`Detector`）と `app/src/shared/calibration.ts`（`calculateCalibration`）
  - `takker`: チームの `feet/takker-dev` ブランチの `mockui/sensor-runtime/`（`SensorPipeline`、`calibration.js` の `features` / `classify` / `Gestures`）。このブランチにはないので、フォルダの場所を引数で受け取る。PM が `/tmp/takker-runtime/mockui/sensor-runtime/` に取り出してある（テストもその隣の `sensor-tests/`）

ハードはいま手元にない。実機のログはまだないので、11 の `--mock` で作ったログで作り、確かめる（合成データなので点数そのものには意味がない。仕組みが正しく動くことの確認）。

## 使い方

```
node score.mjs --detector app --train tap-logs/A --test tap-logs/B
node score.mjs --detector app --cv tap-logs/A                      # 1 つのセッションの中で回す（下記）
node score.mjs --detector takker --takker <sensor-runtime のフォルダ> --channels D0,D4 --cv tap-logs/A
node score.mjs ... --params params.json                            # 検出器の設定を差し替える
```

| オプション | 中身 |
|---|---|
| `--detector app\|takker` | 採点する検出器 |
| `--train <dir>…` / `--test <dir>…` | キャリブレーションに使うセッションと、採点に使うセッション（複数可）。同じセッションを両方に入れたらエラー |
| `--cv <dir>…` | 交差検証。`rep`（繰り返し番号）で分け、1 つの `rep` を採点に、残りをキャリブレーションに使うのを `rep` の数だけ繰り返して合算する。**`--train/--test` を使えるなら、そちらのほうが正しい点数になる**ことを結果に書き添える |
| `--takker <dir>` | `takker` のときの `sensor-runtime` のフォルダ |
| `--channels D0,D4` | `takker` のときに使う 2 入力（takker の検出器は 2 入力しか使わない）。既定 `D0,D4` |
| `--params <json>` | 検出器の設定の上書き（下記）。採点結果に中身をそのまま残す |
| `--out <dir>` | 結果の保存先。既定は `scores/<時刻>_<detector>/` |

## 採点のしかた

採点に使うセッションの `raw.csv` を**先頭から最後まで切らずに**検出器に流す（試行の間や、叩き以外の記録の間も流す。実際の使い方と同じにするため）。出てきたタップを、時刻（サンプル番号）で試行に割り当てる。

- タップの時刻は、検出器が「叩き始め」とみなしたサンプル番号。取れない検出器は確定したときのサンプル番号から推定し、その旨を結果に書く
- 試行 `[cue, to + 0.5 秒)` に入ったタップをその試行のものとする。どの試行にも入らないものは「試行外」
- 使うのは `status: "ok"` の試行だけ（`redo` / `aborted` は流すが採点しない。その間のタップは「試行外」にも数えない）
- `calibration` 試行はキャリブレーション側でだけ使う

### tap の試行

| 指標 | 中身 |
|---|---|
| 検出 | タップが 1 つ以上出た割合 |
| 完全一致 | タップがちょうど 1 つで、領域・回数・強さがすべて合っている割合。**主な点数** |
| 領域 / 回数 / 強さ | それぞれだけを見た正解率（タップがちょうど 1 つの試行が分母） |
| 余計 | タップが 2 つ以上出た試行の数（2 回叩きが 1 回×2 に分かれた、など） |

強さをやめて回数だけにする案があるので、**「強さを無視した一致（領域と回数）」も出す**。

### 叩き以外（`rest` / `typing` / `place` / `lean`）と試行外

出たタップの数を `kind` ごとに出す（少ないほど良い）。試行外は合計と「1 分あたり」。

### 出すもの

| ファイル | 中身 |
|---|---|
| `score.json` | 上の指標すべて、16 パターン×（16 パターン＋なし＋複数）の混同行列、使ったセッション・`--params`・検出器の版（`app` は git のコミット、`takker` はフォルダの中身のハッシュ）・キャリブレーションで決まった値（閾値・テンプレートなど） |
| `score.md` | 同じ内容を人と AI が読める表に。最初に「完全一致 xx%（n 試行）、叩き以外の誤検出 n 回」の 1 行 |
| `predictions.jsonl` | 試行ごとに、正解とタップの一覧（サンプル番号・領域・回数・強さ・確信度など検出器が出すもの） |

画面には `score.md` の 1 行目と保存先を出す。

## 検出器ごとのキャリブレーション

検出器は「キャリブレーション用の試行を受け取って設定を作る」「設定を使って生値を流し、タップを出す」の 2 つを持つ形にそろえる（`detectors/app.mjs`、`detectors/takker.mjs`）。あとで 3 つ目の検出器を足せる形にする。

### app

- `app/` の TypeScript を読み込んで使う。`app/tests/run.cjs` と同じく `app/node_modules/typescript` で一時フォルダにコンパイルしてから `require` する（`app/` で `npm ci` 済みであることが前提。なければ分かるエラーにする）
- キャリブレーション: アプリのキャリブレーションと同じ手順をなぞる。`calibration` 試行で `measure_noise` に当たるノイズを取り、`count: 1` の tap 試行を校正モードの `Detector` に流して `hit` を集め、領域×強さごとに 3 つずつ `calculateCalibration` に渡す（`hits` の選び方は、キャリブレーション側の該当試行の先頭から順に。`CalibrationError` などでキャリブレーションできなければ、その理由を結果に書いて 0 点にする）
- 採点: できた校正値で `run` モードの `Detector` に流し、`tap` を集める。時刻は `Detector` に渡しているサンプル番号から
- `--params` で `Calibration` の値（`threshold`、`strongMin`、`doubleWindowMs`、`refractoryMs`）をキャリブレーションの結果に上書きできる

### takker

- `--takker` のフォルダから `pipeline.js` と `calibration.js` を import して使う。`controller.js`（シリアル・保存・UI 向け）は使わない。中身を書き換えない・コピーしない
- キャリブレーション: takker のアプリの「学習」（takker の画面での呼び方）と同じく、`SensorPipeline` に流して出た `tap` から `features` を作り、領域×強さ（`TARGETS`）ごとに `REQUIRED` 個ずつ集める。どの領域を使うか（2 領域の対角か 4 領域か）は `--channels` とログの領域から決め、結果に書く
- 採点: `classify` → `Gestures` で 1 回 / 2 回を確定させる。`Gestures` が実時間のタイマーを使うなら、サンプル番号から作った時計に差し替えて、実時間を待たずに回す
- `--params` で `SensorPipeline` の設定（`minThreshold` など）と `Gestures` の設定を上書きできる

## テスト（`npm test` に足す）

1. 割り当て: 合成の試行とタップの一覧から、検出・完全一致・領域・回数・強さ・余計・試行外・`redo` の除外が期待どおりに数えられる（検出器を使わない純粋な関数のテスト）
2. 分け方: `--train` と `--test` に同じセッションでエラー。`--cv` で `rep` ごとに分かれ、キャリブレーション側に採点側の試行が入らない
3. `app` の通し: `--mock` の発生源（11 の `mockValues`）で小さなセッションを実時間を待たずに作り、`--cv` で採点して、ファイルができて、完全一致が 0 より大きい
4. `takker` の通し: 環境変数 `TAKKER_RUNTIME` があるときだけ走らせ、なければ skip（skip した理由を出す）

## 完了条件

- `npm test` が通る（`TAKKER_RUNTIME=/tmp/takker-runtime/mockui/sensor-runtime` を付けても通る）
- `--mock` のログで `app` と `takker` の両方の `score.md` を作り、完了報告に 1 行目を書く
- `docs/hardware-test.md` の tap-collect の節に、採点のしかたを 3 行ほど足す（別の机・別の日で記録したセッションを `--test` にするのが正しい点数、ということを含める）

## PM レビューでの修正

点数の数え方・分け方・2 つのアダプタは仕様どおり。次の 3 点を直す。

1. **合成データの強打がいつも飽和する**: `mockValues` の強は振幅 2600 で、叩いた ch が毎回飽和する。そのため既定の `--mock` のログでは、どちらの検出器もキャリブレーションできずに 0 点になる。11 の仕様は「強は時々飽和させる」なので、強の振幅を飽和しない大きさにし、強の試行の 5 回に 1 回くらいだけ飽和させる
2. **合成データが毎回まったく同じ**: 同じパターンなら毎回同じ波形なので、採点しても意味がない。試行ごとに振幅を ±20%、ch の重みを ±15%、2 回目の間隔を 200〜350 ms の範囲でばらつかせる（`seed` と試行の番号から決まる乱数で。同じ seed なら同じログになること）
3. **読みやすさ**: `score.mjs`・`scoring.mjs`・`detectors/*.mjs`・`test/score.test.mjs` を、11 の修正と同じように、ふつうの改行・インデントに直す。動きは変えない

直したら、既定の `node collect.mjs --mock` に相当するログ（4 領域×1・2 回×弱・強×5 回＋叩き以外）をテスト用の生成で作り、`--cv` で `app` と `takker`（`--channels D0,D4`）の両方を採点して、完了報告に `score.md` の 1 行目を書く。どちらも完全一致が 0 より大きいこと（takker は 2 入力なので 4 領域の点が低いのは構わない）。
